# Performance Documentation

## Caching

None implemented. Every dashboard/report/lookup request re-queries PostgreSQL live, on every call, with no in-memory or distributed cache layer.

## Optimizations Present

- `TicketQueryHelper.BaseTicketQuery()` centralizes `.Include()` joins so N+1 query patterns are avoided within a single request — EF Core issues one query with joins rather than lazy-loading each navigation property separately.
- Pagination implemented on the Ticket list and Activity Log endpoints (`Skip`/`Take`), preventing full-table loads on every request.
- Frontend: `ResponsiveContainer` from Recharts avoids fixed-size re-renders; chart data is pre-aggregated server-side (not computed client-side from raw ticket lists), keeping payload size and client CPU work down.

## Lazy Loading

Not used — EF Core lazy-loading proxies are not enabled. All related data is eagerly loaded via explicit `.Include()` calls. This is the safer, more predictable choice given the thin-controller/service pattern (no surprise queries fired during serialization), at the cost of always pulling full related-entity graphs even when only a subset of fields is actually needed by the DTO.

## Database Optimization

Standard FK indexes exist (auto-generated by EF Core on every foreign key column). No composite indexes and no query-plan analysis were performed as part of this project.

**Known scaling risk:** `ReportsService.GetMonthlySummaryAsync` loads **all** tickets in the requested date range into memory (`ToListAsync()`) and then performs in-memory grouping/averaging via LINQ. This is acceptable at current data volumes but will not scale — as ticket counts grow into the tens of thousands, this should be rewritten to push the `GroupBy`/`Average` operations into SQL (EF Core can translate `GroupBy` to `GROUP BY` when kept in the `IQueryable` pipeline rather than materialized early with `ToListAsync()`).

The same in-memory aggregation pattern exists in `DashboardService.GetStatsAsync`.

## Memory Usage

No explicit profiling was performed during development. The in-memory aggregation pattern noted above is the primary memory-scaling risk as ticket volume grows — each dashboard or report request currently pulls the full matching ticket set into application memory before computing statistics.

## Performance Bottlenecks (Identified, Not Yet Addressed)

| Bottleneck | Location | Impact |
|---|---|---|
| In-memory aggregation instead of SQL-side `GROUP BY` | `ReportsService`, `DashboardService` | Grows linearly with ticket count; will degrade as data scales |
| No caching layer | All read endpoints | Every dashboard/report load re-runs full queries, even for historical data that never changes (e.g. last month's closed tickets) |
| SignalR reconnects on every page refresh | Frontend SignalR client | Adds ~500ms delay per navigation in the worst case (noted as a known issue in the original project handoff) |

## Scalability

A single backend instance is assumed throughout — there is no horizontal scaling configuration and no distributed cache/backplane for SignalR. If the API were scaled to multiple instances behind a load balancer, real-time notification delivery would become inconsistent (a client connected to instance A would not receive a push triggered by an action processed on instance B) unless a Redis backplane were added for SignalR (`AddStackExchangeRedis()` in `Program.cs`).

## Recommendations for Future Scaling

1. Rewrite `ReportsService` and `DashboardService` aggregation queries to stay within `IQueryable` and let EF Core translate grouping/averaging to SQL, rather than materializing full lists first.
2. Introduce a short-lived cache (e.g. `IMemoryCache`) for dashboard stats, since most users tolerate slightly stale KPI numbers in exchange for faster loads.
3. Add a Redis backplane for SignalR before any multi-instance deployment.
4. Investigate the SignalR reconnect-on-refresh behavior — likely fixable by persisting the connection differently or accepting it as a one-time cost per session rather than per navigation.
